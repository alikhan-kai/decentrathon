# Задача integrator: head_loss, проверки 5-7, сборка и финальный full

Файлы: `solution/head_loss.py`, `solution/__init__.py` (только integrator правит `MODULES`), `kaggle/`, `notes/`, `tools/`. Ветка `feat/head-loss`.

## Что в профиле (OP, решение, мс/шаг)
- Fused head + loss (`_FusedHeadLoss`) 41.9 мс/шаг (5.7%): почти всё это cuBLAS matmul головы (формы `[512, 1536] x [1536, 151936]` и обратная), наш кернел `head_loss_kernel` 3.21 мс/шаг (0.46%, 138 запусков за 64 шага).
- softmax/CE упал с 55.6 мс/шаг (база) до 3.0 (FP): это уже сделано.
- Память: 8385 MiB против 14345 у базы (memory_ratio 1.711). Вклад head_loss и SwiGLU по отдельности в экономию памяти: не знаю, не замеряли.

## Цели
1. Держать `head_loss` рабочим и в допуске: проверки 5 (entropy, accuracy, row loss в пределах 3%), 6 (loss кривая), 7 (eval loss не выше 2.0599).
   Сейчас: 5, 6, 7 PASS (FP/checks.json), eval loss 2.04969.
2. Принимать PR в `main`, следить за `MODULES`, за пересечениями патчей (см. `docs/INTERFACES.md`).
3. Память: пик не должен вырасти выше 8385 MiB, иначе платим баллы за память (30 из 100).
4. Финальный `full` (или `full_profile`) на сдаваемом коммите, `SUBMISSION.md`, README, публичный ноутбук.

## Первый шаг (день 1)
- Прогнать `tools/kaggle_run.sh quick` на `main` после каждого влитого PR; следить за строкой «наши кернелы» (`tools/summarize.py`).

## Риски
- `head_loss` меняет `Qwen2ForCausalLM.forward` и `SFTTrainer.compute_loss`: другие модули это не трогают. Правки Soup/TRL в других версиях здесь сломаются тихо: версии зафиксированы.
- Метки с `-100`, паддинг, `num_items_in_batch`: уже учтены в черновике, новый тест покрывает только простой случай; для проверки 5 смотреть `checks.json`.
- Нужен запас по проверке 4 после слияния: суммарно >= 34.8 мс/шаг (FINDINGS §2), лучше 40+.

## Критерий готовности
`full_profile` на финальном коммите: проверки 1-10 PASS, speedup >= 1.15, memory_ratio >= 1.7 (не хуже текущих 1.154 и 1.711),
eval loss не выше 2.0599, `lint` и `check_local.sh` зелёные.

## Возможная 4-я задача (только если сумма не доходит до 5%)
Сумма ожидаемого своего времени (оценки, не замеры): nf4 около 39.8 (если не медленнее bnb), rmsnorm около 10, lora несколько мс, head_loss 3.2.
При nf4 около 40 запас большой (около 55 мс/шаг против 34.8). Если nf4 окажется быстрее bnb вдвое или не получится, остаётся
rmsnorm + lora + head_loss около 17-20 мс/шаг и 5% **не хватает**. Кандидаты по профилю:
- **fused rotary** (`apply_rotary_pos_emb`, 28 вызовов за шаг): **32.0 мс/шаг** (fwd 13.6, bwd 18.4), fp32; точка патча: функция `modeling_qwen2.apply_rotary_pos_emb`.
  Первый выбор: больше всего времени среди оставшихся и простая локальная операция. Свой кернел займёт часть этих 32 мс (не знаю сколько, измерить).
- **слияние остаточных сложений** (`DecoderLayer` исключая вложенные): 7.5 мс/шаг, мало; делается вместе с rmsnorm (шаг 2).
- **эпилог Attention** (`Qwen2Attention` исключая вложенные: 77.7 мс/шаг, из них SDPA около 55: `_efficient_attention_backward` 38.4 + forward 16.7). Остаток около 22 мс/шаг: транспонирования и копии; чем именно, профиль не говорит.
Решение о 4-й задаче принимаем по `quick` после слияния первых трёх.
